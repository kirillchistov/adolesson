 # Выкладка в Yandex Cloud

Сейчас пилот идёт на Vercel и Supabase: [cloud-deploy.md](cloud-deploy.md). Этот файл — маршрут на момент, когда на сервере появятся данные реальной семьи и их снова нужно хранить в РФ.

Инструкция для аккаунта в Yandex Cloud. Репозиторий ресурсы не создаёт: команды ниже запускает владелец аккаунта. Секреты остаются в Lockbox и в окружении сервиса.

Регион — `ru-central1`. Серверный слой семьи живёт в РФ. Личный слой подростка (чек-ины, журнал, блоки, баллы карты, «Моё», аватар) на сервер не выкладывается и в эту инструкцию не входит.

## Как это соотносится с Vercel, Render и Supabase

Одна платформа на каталог, несколько приложений подключаются к ней одинаковым способом. У каждого приложения своя база, свой контейнер и свой адрес. Общий вход — отдельный сервис, его подключают, когда один и тот же человек должен открывать два продукта.

| Привычная часть | В Yandex Cloud | Что общее, что своё |
|---|---|---|
| Vercel, статический фронт | Object Storage, раздача через API Gateway | Своё ведро на приложение |
| Render, контейнер API | Container Registry и Serverless Containers | Свой образ и свой сервисный аккаунт |
| Supabase, одна база с разными схемами | Один кластер Managed PostgreSQL, отдельная база и пользователь на приложение | Кластер общий. Схема внутри одной базы — запасной вариант, см. ниже |
| Supabase Auth | База `identity` и небольшой сервис, который выдаёт JWT. API Gateway умеет проверять такой токен | Сервис один на платформу. Пока его нет, у adolesson свой вход семьи |
| Роли Supabase RLS | Проверка доступа в API приложения | У adolesson это тесты «общий стол видит только своя семья» |

Роли Yandex Cloud IAM выдают людям и сервисным аккаунтам доступ к ресурсам облака: реестру, секрету, шлюзу. Вход родителя и подростка IAM не заменяет.

Yandex ID можно позже добавить как один из способов входа в `identity`. Для семьи он не обязателен: логин и секрет участника задаёт родитель, у подростка может не быть аккаунта Яндекса.

## Что уже готово в репозитории

- Образ API: `make api-image` (контекст сборки — корень, файл `backend/Dockerfile`). Образ слушает переменную `PORT`. В Dockerfile по умолчанию `5001`. Serverless Containers при HTTP-режиме подставляет свой `PORT`, процесс его читает.
- Сессия: `COOKIE_SECURE=1` включает cookie `Secure` и `trustProxy`. Если задан `CORS_ORIGIN`, cookie становится `SameSite=None` и браузер принимает её только с перечисленных адресов. Без `CORS_ORIGIN` фронт и API на одном адресе, cookie `SameSite=Lax`.
- Клиент: пустой `VITE_API_URL` оставляет запросы на тот же адрес (`/api`). Чужой адрес API задают при сборке фронта без завершающего слэша.
- Миграции применяются при старте процесса. Повторный старт пропускает уже записанные файлы из `backend/migrations/`.
- `GET /api/health` выполняет `SELECT 1` и при живой базе отвечает `{"status":"ok"}`.

Проверка образа локально: контейнер без `DATABASE_URL` должен сразу завершиться с текстом «Задайте DATABASE_URL».

## Платформа, один раз на каталог

Платные части: кластер PostgreSQL (хосты, диск, копии), реестр образов, вызовы Serverless Containers, хранение объектов, шлюз. Публичный IP кластера не нужен, если контейнер сидит в той же сети.

Схема:

```text
браузер
  └─ API Gateway  https://<адрес-приложения>
       ├─ /            Object Storage, свой бакет приложения
       └─ /api/*       Serverless Container, свой образ приложения
                              │
                              ▼
                    Managed PostgreSQL, один кластер
                      ├─ база adolesson
                      ├─ база следующего приложения
                      └─ база identity    — когда появится общий вход
```

Общие ресурсы:

- Сеть и каталог в `ru-central1`.
- Кластер Managed PostgreSQL 16, как локальный `postgres:16` в `docker-compose.yml`. Режим пулера — **SESSION**. В режиме TRANSACTION клиент `pg` и транзакции API работают непредсказуемо: пулер не держит подготовленные запросы и соединение на время транзакции. Документация пулера: [Odyssey](https://yandex.cloud/ru/docs/managed-postgresql/concepts/pooling).
- Container Registry.
- Lockbox. Отдельный секрет на приложение, ключ `database_url` — строка подключения целиком.

На приложение:

- База и пользователь с тем же именем (`adolesson`, следующее имя — своим). Пользователь владеет только своей базой. На кластере до 1000 баз: [управление базами](https://yandex.cloud/ru/docs/managed-postgresql/operations/databases).
- Сервисный аккаунт runtime: `container-registry.images.puller` на реестр и `lockbox.payloadViewer` на свой секрет.
- Сервисный аккаунт шлюза: `serverless.containers.invoker` на контейнер и `storage.viewer` на бакет.
- У того, кто создаёт ревизию, на этих аккаунтах нужна роль `iam.serviceAccounts.user`.

Лимит соединений пользователя на хосте по умолчанию — 50. Пул `pg` в процессе — до 10. Для семьи достаточно максимума в два экземпляра контейнера.

DataLens и общий WebSQL к базе семьи не подключать: это ещё один читатель записей общего стола.

## adolesson: первое приложение

### 1. База

Создать кластер по [инструкции](https://yandex.cloud/ru/docs/managed-postgresql/operations/cluster-create): PostgreSQL 16, пулер SESSION, защита от удаления. База `adolesson`, пользователь `adolesson`. Публичный доступ к хосту не включать: контейнер подключается из той же сети.

Хост для записи: `c-<идентификатор-кластера>.rw.mdb.yandexcloud.net`, порт пулера `6432`. Контейнер подключается из сети кластера, публичный адрес хоста не включается. Так описано в [подключении Serverless Containers к PostgreSQL](https://yandex.cloud/ru/docs/tutorials/serverless/container-pg-connect): для частной сети `sslmode` не нужен.

Строка, которая попадёт в Lockbox:

```text
postgres://adolesson:<пароль>@c-<идентификатор-кластера>.rw.mdb.yandexcloud.net:6432/adolesson
```

Если хост всё же открыт в интернет, к строке добавляют `?sslmode=require`. Образ не содержит корневой сертификат Yandex Cloud, поэтому `verify-full` заработает только после того, как сертификат появится в образе. Предпочтительный путь — частная сеть.

### 2. Образ

```bash
make api-image
yc container registry configure-docker
docker tag adolesson-api cr.yandex/<идентификатор-реестра>/adolesson-api:1
docker push cr.yandex/<идентификатор-реестра>/adolesson-api:1
```

Ревизию можно собрать только из образа в Container Registry.

### 3. Секрет и контейнер

Секрет Lockbox `adolesson-api`, ключ `database_url` — строка из шага 1. Передача секрета в контейнер создаёт новую ревизию: [Lockbox → Serverless Containers](https://yandex.cloud/ru/docs/serverless-containers/operations/lockbox-secret-transmit).

Ревизия:

- образ `cr.yandex/<идентификатор-реестра>/adolesson-api:1`;
- режим HTTP-сервер, `PORT` задаёт платформа, в ревизии его не переопределять;
- сервисный аккаунт runtime;
- сеть кластера PostgreSQL;
- память 512 МБ, таймаут выполнения не меньше 30 секунд (первый вызов применяет миграции);
- обычная переменная `COOKIE_SECURE=1`;
- секрет: переменная `DATABASE_URL` ← ключ `database_url`;
- `CORS_ORIGIN` не задавать: фронт и API откроются с адреса шлюза.

`COOKIE_SECURE` здесь включён, потому что шлюз отдаёт сайт по HTTPS.

Экземпляр после простоя засыпает и рвёт TCP к базе. Следующий запрос может один раз не достучаться до PostgreSQL; повторный `GET /api/health` уже видит новое соединение. Подготовленный экземпляр уменьшает холодный старт и тоже засыпает, поэтому на обрыв соединения он не отвечает.

### 4. Фронт

GitHub Pages публикует прототип `prototype/dist`. Продуктовый `frontend/` собирается отдельно и кладётся в приватный бакет. Сайт смотрят через шлюз, не через отдельный адрес бакета: иначе cookie сессии окажется на другом сайте.

```bash
cd frontend && npm run build
```

`VITE_API_URL` не задают. `base` в Vite — `./`, маршруты — hash (`#/parent/table`), поэтому шлюзу достаточно `index.html` и файлов из `frontend/dist`. При загрузке у `.js` тип `application/javascript`, у `.css` — `text/css`.

### 5. Шлюз

Спецификация API Gateway. Идентификаторы подставить свои. Расширения: [контейнер](https://yandex.cloud/ru/docs/api-gateway/concepts/extensions/containers), [Object Storage](https://yandex.cloud/ru/docs/api-gateway/concepts/extensions/object-storage).

```yaml
openapi: 3.0.0
info:
  title: adolesson
  version: "1.0.0"
paths:
  /api/{proxy+}:
    x-yc-apigateway-any-method:
      parameters:
        - name: proxy
          in: path
          required: false
          schema:
            type: string
            default: "-"
          explode: false
          style: simple
      x-yc-apigateway-integration:
        type: serverless_containers
        container_id: <идентификатор-контейнера>
        service_account_id: <сервисный-аккаунт-шлюза>
  /:
    get:
      x-yc-apigateway-integration:
        type: object_storage
        bucket: <бакет-фронта>
        object: index.html
        service_account_id: <сервисный-аккаунт-шлюза>
  /{file+}:
    get:
      parameters:
        - name: file
          in: path
          required: true
          schema:
            type: string
      x-yc-apigateway-integration:
        type: object_storage
        bucket: <бакет-фронта>
        object: "{file}"
        error_object: index.html
        service_account_id: <сервисный-аккаунт-шлюза>
```

Путь до контейнера должен доходить целиком, начиная с `/api`. Свой домен и сертификат подключаются к шлюзу позже. Для первой проверки хватает домена шлюза.

### 6. Проверка

1. `curl https://<адрес-шлюза>/api/health` → `{"status":"ok"}`. В логах контейнера видна применённая миграция, в ответе нет текста ошибки базы.
2. В браузере открыть адрес шлюза, создать семью на `#/parent/table`. В ответе `POST /api/families` есть `Set-Cookie` с `Secure` и `HttpOnly`. Обновить страницу: `GET /api/session` возвращает ту же семью.
3. Подросток открывает `#/join/{token}` на другом устройстве или после выхода. В одном браузере по-прежнему одна сессия.
4. В базе `adolesson` после этих шагов есть семья, участники и сессия. Чек-инов, журнала, блоков и баллов карты там нет.

Прямой адрес контейнера по умолчанию закрыт IAM-токеном. Семья ходит только на шлюз.

## Второе приложение и общий вход

Новое приложение повторяет шаги adolesson на тех же кластере, реестре и каталоге:

1. База и пользователь только этого приложения. Его `DATABASE_URL` не открывает базу `adolesson`.
2. Свой секрет, свой runtime-аккаунт, свой контейнер, свой бакет.
3. Свой адрес: отдельный шлюз или свой домен. Cookie adolesson называется `session`. Два приложения на одном хосте перезапишут её друг другу. Общий хост с разными путями для сессий не использовать.
4. Свои миграции в своём репозитории. Таблицы другого продукта в базу `adolesson` не добавлять.

Так приложения делят инфраструктуру и не делят записи.

Общий вход подключается, когда одному человеку нужен один логин в два продукта. До этого момента вход adolesson — логин и секрет участника семьи, сессия лежит в базе `adolesson`.

Состав сервиса `identity`:

- База `identity` на том же кластере, свой пользователь.
- Контейнер, который выдаёт короткоживущий JWT: `iss` — адрес сервиса, `aud` — код приложения, `sub` — идентификатор учётной записи.
- API Gateway проверяет подпись через JWT-авторизатор. Форма расширения показана в [учебном примере с JWT](https://yandex.cloud/ru/docs/tutorials/serverless/jwt-authorizer-firebase); издатель токена — этот сервис, не Firebase и не Google.
- Приложение хранит у себя только `sub` и свои предметные таблицы. adolesson по-прежнему хранит семью и членство. Привязка «учётная запись платформы → участник семьи» — отдельное продуктовое решение. Личный слой подростка в `identity` не копируется.

Схема внутри одной базы (`search_path`, как схема `career_os` в общем проекте Supabase) уместна, только если два приложения должны менять данные в одной транзакции. Изоляция слабее: владелец базы видит обе схемы. Для семьи и соседнего продукта база на кластер надёжнее.

## Чего не делать

- Не класть пароль базы, `DATABASE_URL` и ключи сервисных аккаунтов в репозиторий и в образ.
- Не выдавать одному пользователю PostgreSQL права на базы нескольких приложений.
- Не включать пулер в режим TRANSACTION ради «как в Supabase pooler». Для этого API нужен SESSION.
- Не слать на API чек-ины, журнал, блоки, баллы, наблюдения родителя и аватар. Контракт их не принимает, выкладка это не меняет.
- Не считать пункт дорожной карты закрытым, пока семья не открыла шлюз с двух устройств и `/api/health` не ответил `ok`.
