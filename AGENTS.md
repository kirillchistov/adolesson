# Правила работы с репозиторием (для людей и ИИ-агентов)

Проект: адаптивное веб-приложение для семьи — отдельные входы для родителей и подростка,
8-недельный маршрут поддержки учёбы. Продуктовая основа — [docs/app-concept.md](docs/app-concept.md),
содержательная — [docs/support-concept.md](docs/support-concept.md), источники —
[docs/sources.md](docs/sources.md).

Правила взяты из [fullstack-javascript-project-387](https://github.com/kirillchistov/fullstack-javascript-project-387/blob/main/AGENTS.md)
и дополнены правилами, специфичными для этого продукта (контент, приватность, безопасность).

## Состояние проекта

В репозитории документы и кликабельный прототип этапа 0 в `prototype/`.
Каркаса `frontend/` и сервера ещё нет: они появляются по
[дорожной карте](docs/project-roadmap.md). Каркас переносится из
[betty-rules](https://github.com/kirillchistov/betty-rules) по плану §9.4 концепции.
Разделы ниже про контракт, запуск `frontend/` и проверки вступают в силу вместе
с соответствующим кодом; до этого их не нужно имитировать заглушками.

## Подход: Design First

Источник истины для API общего стола (семья, договорённости, светофор, просьбы,
встречи) — TypeSpec-контракт в `spec/`. Любое изменение API начинается с правки
`.tsp`-файлов, затем:

1. `npm run spec:build` — пересобрать `docs/api/openapi.yaml` (руками не редактируется);
2. `cd frontend && npm run api:types` — обновить типы клиента.

Бэкенд и фронтенд опираются только на контракт: бэкенд валидирует запросы схемами
из `openapi.yaml`, фронтенд ходит в API только через типизированный клиент
`frontend/src/api/client.ts`.

Если выбран BaaS (Supabase и т. п., см. §9.2 концепции) — источником истины остаются
миграции схемы и политики доступа (RLS) в репозитории; правка через веб-консоль без
миграции не допускается.

## Продуктовые правила (обязательны для кода и контента)

### Приватность подростка

- Личный слой подростка (чек-ины, минутный журнал, блоки, самодиагностика, «Моё»)
  хранится **только на устройстве**. Не добавлять код, который отправляет эти данные
  на сервер, в аналитику, логи ошибок или сторонние SDK.
- Данные попадают на общий стол только явным действием автора с предпросмотром.
- Никаких автоматических уведомлений родителям о содержании записей подростка.
- В продуктовую аналитику — только обезличенные события без содержимого записей.

### Контент

- Язык действий, не характера: в текстах интерфейса нет «ленивая», «мотивация»,
  «дисциплина», «опять», «никогда» в адрес подростка.
- Без стриков, очков за объём, обратных отсчётов до экзаменов и «удвоения» после
  удачного дня (принципы §7 концепции).
- Каждый содержательный приём или утверждение о здоровье опирается на источник
  из [docs/sources.md](docs/sources.md) (код `U4`, `S1`…). Новый источник сначала
  добавляется в реестр с проверенной ссылкой.
- Формулировки диагностики — профиль и наблюдения, не диагноз; дисклеймер обязателен.
- Тексты кризисного экрана и §16 меняются только вместе с проверкой по W5/W6
  и с пометкой в описании PR, что нужна вычитка специалистом.

## Формат коммитов: Conventional Commits

Все коммиты (включая сделанные агентами) следуют
[Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/) — по ним
release-please будет формировать changelog и версию.

Формат: `type(scope): description` — описание на английском, в повелительном наклонении
(`add`, `fix`, `move`), со строчной буквы, без точки в конце.

Типы и их влияние на версию:

- `feat:` — новая функциональность (minor);
- `fix:` — исправление ошибки (patch);
- `feat!:` / `fix!:` или футер `BREAKING CHANGE:` — несовместимое изменение (major);
- `docs:`, `test:`, `ci:`, `chore:`, `refactor:` — не попадают в версию, но допустимы
  и желательны для непродуктовых изменений. Настройка репозитория, конфиги и
  зависимости — `chore:`/`ci:`, не `feat:`.

Области (scope): `spec`, `backend`, `frontend`, `prototype`, `content`, `e2e`, `ci`, `docs`, `deps`.
`content` — тексты маршрута, квесты, карточки, диагностика, источники.

Примеры:

```text
feat(frontend): add teen check-in screen with color picker
feat(spec): add weekly agreement accepted by both sides
fix(frontend): hide mantras over the block timer
feat(content): add parent quest "she said leave me alone"
chore: configure editorconfig and commitlint
docs: add sleep and stress sources to registry
```

Правила для агентов:

- один коммит — одно логическое изменение;
- если правка затрагивает контракт и реализацию, коммитить вместе с пересобранными
  `docs/api/openapi.yaml` и типами клиента;
- агенты не делают коммитов, push и PR: изменения остаются в рабочей копии,
  владелец репозитория просматривает их и коммитит сам;
- по завершении работы агент перечисляет изменённые файлы, отмечает всё, что
  не должно попасть в репозиторий, и предлагает сообщение коммита в этом формате;

## Запуск приложения локально

Прототип этапа 0, пока нет каркаса `frontend/`:

```bash
cd prototype && npm install && npm run dev   # UI на http://localhost:5173
```

Ориентир после появления каркаса (как в betty-rules и project-387):

```bash
cd frontend && npm install && npm run dev   # UI на http://localhost:5173
```

## Проверки перед коммитом

Для кода (по мере появления):

- `cd frontend && npm run lint && npm run build` — линт (oxlint) и типы;
- `cd frontend && npm run test:ct` — компонентные тесты (Playwright CT);
- `cd backend && npm test` — правила API, в том числе доступ к общему столу
  только участникам семьи;
- `cd e2e && npm test` — сценарии двух ролей (родитель и подросток в разных сессиях).

Для документов и контента: ссылки в `docs/sources.md` открываются, коды источников
в текстах существуют в реестре.
